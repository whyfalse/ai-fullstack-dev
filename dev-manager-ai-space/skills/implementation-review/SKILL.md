## 审查对象

两种对象共享同一套审查纪律：

1. **设计产物**：`architecture/module/<模块>/<moduleId>.md`、`test.md` 等设计文档。
2. **实现代码**：目标仓代码，路径经 `setting.local.json` 的 `modules.<id>.projectPath` 解析，只读不写。

## 审查维度与严重度

**阻塞级（问题，须修复或人工裁定）**：

- **契约符合性**：是否忠实于 `/architecture/contracts/apis/` 与 `/architecture/contracts/database/` 契约。
- **设计一致性**：实现/设计是否符合对应模块功能文档与架构原则（契约先行、模块划分、数据独立性、可演进性，见 `architectural-design` 技能）。
- **安全**（实现审查必审）：注入（SQL/命令）、XSS、越权、鉴权绕过等。

**建议级（非阻塞，随结论列出）**：

- 代码质量、反模式、性能、可维护性。

## 深审 vs 轻审

- **高风险变更**（涉契约 / DB / 鉴权）：全量深审，逐条核对契约与安全。
- **其余变更**：轻审，聚焦契约符合性与明显缺陷。

## 审查流程

1. 定位审查对象：读对应模块功能文档、契约（API + DB）、目标仓代码。
2. 对照契约与设计，逐维度检查，判定严重度。
3. 输出结论（不落盘）：
   - 通过 → 完成摘要声明"审查通过 + 建议清单"。
   - 有阻塞问题 → 输出缺陷清单（按严重度分级），区分两类：
     - **可修复缺陷**（代码违反契约 / 设计 / 安全，但契约与设计本身正确）→ 缺陷清单交由派发方转开发者修复，不走 GATE。
     - **需拍板**（契约本身需改、豁免判断、破坏性设计分歧）→ 输出 GATE(实现审查) 段落（手动模式交互提问；派遣模式输出后立即结束）。

## GATE(实现审查) 段落格式

```markdown
## GATE
类型: 实现审查
背景: <一句话说明为什么需要人工决策>
问题:
  1. <问题描述> 选项: A) ... / B) ... 建议: A
相关文件: <涉及的文件路径列表>
批准后继续: <批复后将立即执行的下一步摘要>
```

GATE(实现审查) 仅用于需拍板的阻塞问题（可修复缺陷不走 GATE、直接转开发者修复）。处置动作参考「缺陷处置」语义：豁免 / 人工介入 / 转架构师处理（契约本身需改）。

## 自检清单

- [ ] 契约符合性、设计一致性、安全（实现审查）均已核对，无遗漏
- [ ] 问题与建议分级正确；可修复缺陷进入缺陷清单转开发者修复，需拍板问题输出 GATE，未静默保留
- [ ] 只报告不修改：未改动任何契约 / 设计 / 代码文件
- [ ] 高风险变更已深审，其余变更已轻审
- [ ] 结论通过完成摘要 / 缺陷清单 / GATE 输出，未落盘审查报告文件
