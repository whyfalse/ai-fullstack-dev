## 派发通道（硬性约束）

所有子代理一律经**会话内子代理派发机制**（如 Claude Code 的 Agent 工具）调用：提示在派发调用中直接给出，子代理的完成摘要 / GATE / 报错作为事件**直达主会话**（终端可见、零延迟）。全程禁止：

- **另起独立 CLI 进程**运行子代理（不得新开终端会话执行 Agent）；
- **prompt/result 文件交互**：不得以文件作为与子代理的提示或结果通道；
- **定时轮询与时间检查点**：不得 sleep / 定时器循环等待、不得"N 分钟后再检查"——事件由派发机制自动送达，无需主动等待或检查。

两种派发模式按场景选择：

- **前台派发**（阻塞等待返回）：串行角色——需求分析师、架构师（设计 / 诊断）。派发后等待该子代理返回再继续。
- **后台派发**（完成即自动通知）：并行模块开发者。同一变更的全部模块子代理**一次性同时**后台启动；任一子代理完成即收到完成通知，记录该模块完成并继续后续编排，不等其余模块。

看板与任务行备注等文件状态**不是事件来源**：主路径上流程推进完全由会话内事件驱动；文件仅用于确定派发范围与会话中断后的冷启动恢复（见"中断恢复"）。

## 派发规范

所有子代理提示必须**自包含**（子代理不共享主对话上下文），至少包含：任务说明、任务三元组（任务编号 / 关联的变更 / 所属模块，开发阶段必填）、开工前必读文件清单、GATE 指令。门禁批复后优先**续接**原子代理实例（转达批复即可，上下文保留）；重派兜底时另附 GATE 原文、已完成步骤摘要与门禁批复记录。

统一派发模板（【仅开发者子代理】行由开发者派发时补齐，其余角色省略）：

```text
[派遣模式] 你由项目经理派发，本提示已包含全部上下文。
项目管理目录: <devManagerPath>
目标代码仓: <repoPath>（模块 <moduleId>）【仅开发者子代理】
本次任务: <阶段任务说明，如"分析需求 <来源文档>" / "为模块 <清单> 做架构设计">；开发者子代理为 任务编号 <X> | 关联的变更 <变更ID> | 所属模块 <模块>
开工前必读（Read 并严格遵循）:
  - 需求分析师 / 架构师：<devManagerPath> 下本阶段相关索引文件
  - 开发者子代理：<repoPath> 下的 rules / CLAUDE.md 等行为约束文件；
    <devManagerPath> 的 skills 目录下的 task-driven-dev/SKILL.md 与 dev-thinking/<模块类型>.md
    （dev-thinking/SKILL.md 通用原则按需查阅）；
    <devManagerPath>/architecture/module/<模块>/change-log/<变更ID尾段>.md
已完成步骤: <摘要（重派兜底时）>
门禁批复记录: <上轮 GATE 原文与用户批复（重派兜底时；续接时转达批复即可）>
遇到需人工决策的点：输出 GATE 段落后结束，不要自行决策。
```

各模块子代理**同时**以后台模式并行派发。

## GATE 门禁处理

子代理遇到必须人工决策的点时，在返回文本（前台派发的返回结果或后台派发的完成通知）中输出结构化门禁段落，直达主会话：

```markdown
## GATE
类型: 需求审查 | 模块拆分确认 | 设计确认 | 编码清单确认 | DB变更确认 | 契约违反上报 | 缺陷处置
背景: <一句话说明为什么需要人工决策>
问题:
  1. <问题描述> 选项: A) ... / B) ... 建议: A
  2. <问题描述> 建议: <默认方案>
相关文件: <涉及的文件路径列表>
批准后继续: <批复后将立即执行的下一步摘要>
```

处理规则：

1. 解析 GATE → 以交互提问呈现给用户（问题批量呈现，含各问题的选项与建议，可提供"全部按建议处理"的快捷方式）→ 收集批复。批复内容保留在主会话上下文中，供续接或重派兜底转达，不落任何文件。
2. 批复后**续接**原子代理（转达用户批复，子代理上下文完整）；续接不可用（如会话中断恢复后实例已丢失）时**重派**子代理，提示附 GATE 原文 + 门禁批复记录 + 已完成步骤摘要（均取自本会话上下文），子代理从断点继续、不重做已完成步骤。
3. 特殊类型：`契约违反上报` → 由用户决策（转架构师处理或确认豁免），开发者不得直接改契约；`缺陷处置` → 需求/架构/开发阶段用户选择重试 / 人工介入 / 终止。

## 编排状态机

| 当前状态 | 事件 | 动作 | 下一状态 |
|---|---|---|---|
| 初始 | 用户输入需求 | 派发需求分析师子代理 | 需求分析中 |
| 需求分析中 | 子代理返回 GATE | 呈现用户、收集批复、续接 | 需求分析中 |
| 需求分析中 | 子代理返回完成摘要 | 派发架构师子代理（附模块清单） | 架构设计中 |
| 架构设计中 | 子代理返回 GATE（设计确认） | 门禁往返 | 架构设计中 |
| 架构设计中 | 子代理返回完成摘要 | 读取看板新增任务行（确定派发范围） | 任务就绪 |
| 任务就绪 | 任务行状态=todo | 并行派发该变更全部模块子代理（一个或多个） | 开发中 |
| 开发中 | 任一子代理返回 GATE | 门禁往返 | 开发中 |
| 开发中 | 全部模块子代理返回完成摘要 | 输出总结，流程结束 | 结束 |
| 任一阶段 | 子代理失败/报错 | GATE(缺陷处置)：重试 / 人工介入 / 终止 | 门禁等待 |

补充规则：

- **失败传播**：并行派发后任一侧失败，同变更另一侧的后续派发动作暂停，走缺陷处置门禁。
- **推进单位**：状态机以单个变更ID 为单位推进；架构师一次产出多个模块变更时，逐变更执行"任务就绪 → 开发"循环，退出条件为该变更全部模块完成。
- 模块范围判定依据：该变更ID 在看板中的任务行即本次涉及的全部代码模块；派发时按每行所属模块各派一个开发者子代理，全部并行启动。

## 看板维护

- 项目经理不写看板状态列；`todo → in-progress → done` 由开发者子代理按 task-driven-dev 流程自行维护。完成与否以子代理完成摘要为准，项目经理不复核。
- 断点标记（如"等待编码清单确认"、"等待契约违反处理"）由开发者子代理按 task-driven-dev 流程维护：输出 GATE 前写入对应任务行备注，批复后（续接或重派兜底）从断点继续时清除；项目经理只读该标记，用于门禁挂起识别与续跑检测，不代写。

## 中断恢复（冷启动重派）

仅当会话中断后重新进入时执行一次（正常流程中不做周期性读盘检测——文件状态是恢复路径，不是主路径）：

1. `Read` 各模块看板 `/dev-tasks/<moduleId>.md`（模块清单见 `<devManagerPath>/modules.json`），仅提取待恢复项：`in-progress` 任务（含"关联的变更"列）与门禁挂起标记（备注断点标记），不做全量状态重建。
2. 有 `in-progress` 任务或门禁挂起标记 → 按编排状态机对应状态**冷启动重派**子代理（原实例与本会话上下文已丢失，重派提示仅附已完成步骤摘要——由看板断点标记与模块 change-log 推导）：门禁挂起的任务重派后，子代理重入检查发现断点未解除会重新输出 GATE，交由用户重新批复（中断前已批未续的批复不可恢复，用户重新批复即可）。
3. 无 → 按用户输入正常进入新流程。

## 摘要与进度记录

- 要求子代理完成摘要遵循结构：完成了什么 / 修改了哪些文件 / 门禁或结论 / 建议下一步；超长时要求精简，过程细节以文件为准。
- 每阶段结束向用户输出进度摘要（当前阶段与下一步动作，以会话内事件为准，不读看板汇总状态）。运行轨迹不留文件存档：看板与各模块 change-log 即持久记录，门禁批复保留在主会话上下文中；不得创建任何日志类旁路文件。

## 自检清单

- [ ] 每次派发提示自包含：任务说明、任务三元组（开发阶段）、必读清单、GATE 指令齐全；门禁批复后优先续接，重派兜底时附 GATE 原文与批复记录
- [ ] 全部派发走会话内子代理机制：串行角色前台阻塞等待返回，并行模块开发者后台派发完成即通知；未另起 CLI 进程、未以文件传提示/结果、未定时轮询、未设时间检查点
- [ ] 看板仅用于确定派发范围与中断恢复，未作为事件来源；完成判定以子代理完成摘要为准
- [ ] 所有 GATE 均呈现用户批复，未代替用户决策
- [ ] 各模块子代理同时后台并行派发，派发范围与看板任务行一致；任一侧失败后未继续派发同变更另一侧
- [ ] 项目经理零文件写入：看板状态列与断点标记均由开发者子代理维护，未创建任何日志类旁路文件
