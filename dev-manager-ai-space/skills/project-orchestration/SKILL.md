## 派发规范

所有子代理提示必须**自包含**（子代理不共享主对话上下文），至少包含：任务说明、任务三元组（任务编号 / 关联的变更 / 所属模块，开发阶段必填）、开工前必读文件清单、GATE 指令。门禁批复后优先**续接**原子代理实例（转达批复即可，上下文保留）；重派兜底时另附 GATE 原文、已完成步骤摘要与门禁批复记录。

**dev-manager 空间内角色**（需求分析师 / 架构师 / 测试者）派发模板：

```text
[派遣模式] 你由项目经理派发，本提示已包含全部上下文。
项目管理目录: <devManagerPath>
本次任务: <阶段任务说明，如"分析需求 <来源文档>" / "为模块 <清单> 做架构设计" / "测试变更 <变更ID>">
开工前必读: <按角色列出 devManagerPath 下的相关索引文件>
已完成步骤: <摘要（重派兜底时）>
门禁批复记录: <上轮 GATE 原文与用户批复（重派兜底时；续接时转达批复即可）>
遇到需人工决策的点：输出 GATE 段落后结束，不要自行决策。
```

**开发者子代理**（前端 / 后端）派发模板：

```text
[派遣模式] 你由项目经理派发，本提示已包含全部上下文。
项目管理目录: <devManagerPath>
目标代码仓: <repoPath>（前端|后端）
本次任务: 任务编号 <X> | 关联的变更 <变更ID> | 所属模块 <模块>
开工前必读（Read 并严格遵循）:
  - <repoPath> 下的 rules / CLAUDE.md 等行为约束文件
  - <repoPath> 的 skills 目录下本角色所需 SKILL.md（按角色列出）
  - <devManagerPath>/architecture/module/<模块>/change-log/<变更ID尾段>.md
已完成步骤: <摘要（重派兜底时）>
门禁批复记录: <上轮 GATE 原文与用户批复（重派兜底时；续接时转达批复即可）>
遇到需人工决策的点：输出 GATE 段落后结束，不要自行决策。
```

并行场景将 fe 与 be 两个子代理**同时**派发；串行场景先派 be。

## GATE 门禁处理

子代理遇到必须人工决策的点时，在返回文本中输出结构化门禁段落：

```markdown
## GATE
类型: 模块拆分确认 | 设计确认 | 编码清单确认 | DB变更确认 | 契约违反上报 | 缺陷处置 | 测试范围确认
背景: <一句话说明为什么需要人工决策>
问题:
  1. <问题描述> 选项: A) ... / B) ... 建议: A
  2. <问题描述> 建议: <默认方案>
相关文件: <涉及的文件路径列表>
批准后继续: <批复后将立即执行的下一步摘要>
```

处理规则：

1. 解析 GATE → 将 GATE 原文追加记录到 `/dev-tasks/pipeline-log.md`（呈现**前**写入，保证呈现期间中断也有记录）→ 以交互提问呈现给用户（问题批量呈现，含各问题的选项与建议，可提供"全部按建议处理"的快捷方式）→ 收集批复，并在该记录下补记一行批复内容。
2. 批复后**续接**原子代理（转达用户批复，子代理上下文完整）；续接不可用（如会话中断恢复后实例已丢失）时**重派**子代理，提示附 GATE 原文 + 门禁批复记录 + 已完成步骤摘要，子代理从断点继续、不重做已完成步骤。
3. 特殊类型：`契约违反上报` → 由用户决策（转架构师处理或确认豁免），开发者不得直接改契约；`缺陷处置` → 需求/架构/开发阶段用户选择重试 / 人工介入 / 终止，测试阶段用户选择回架构师修复 / 标记已知问题。
4. `测试范围确认` 可按默认增量规则（仅测本次变更ID 影响的功能点）预批复，摘要中注明可否决。
5. **格式校验**：按流程应出现门禁而子代理返回的完成摘要中无 GATE 段落 → 视为可疑，回读相关文件状态核实后再决定是否采信。

## 编排状态机

| 当前状态 | 事件 | 动作 | 下一状态 |
|---|---|---|---|
| 初始 | 用户输入需求 | 派发需求分析师子代理 | 需求分析中 |
| 需求分析中 | 子代理返回 GATE | 呈现用户、收集批复、续接 | 需求分析中 |
| 需求分析中 | 子代理返回完成摘要 | 派发架构师子代理（附模块清单） | 架构设计中 |
| 需求分析中 | 子代理失败/报错 | GATE(缺陷处置)：重试 / 人工介入 / 终止 | 门禁等待 |
| 架构设计中 | 子代理返回 GATE（设计确认） | 门禁往返 | 架构设计中 |
| 架构设计中 | 子代理返回完成摘要 | 回读看板新增任务行 | 任务就绪 |
| 架构设计中 | 子代理失败/报错 | GATE(缺陷处置)：重试 / 人工介入 / 终止 | 门禁等待 |
| 任务就绪 | 任务行状态=todo 且变更为并行 | 同时并行派发 fe + be 子代理 | 开发中 |
| 任务就绪 | 变更为串行（前端 blocked） | 派发 be 子代理 | 开发中(串行) |
| 任务就绪 | 变更仅涉及单侧（该变更仅一行任务） | 派发该侧子代理 | 开发中 |
| 开发中(串行) | be 返回完成 | 翻转 fe 任务 blocked→todo（回读校验）后派发 fe | 开发中 |
| 开发中 | 任一子代理返回 GATE | 门禁往返 | 开发中 |
| 开发中 | 任一子代理失败/报错 | GATE(缺陷处置)：重试 / 人工介入 / 终止 | 门禁等待 |
| 开发中 | 全部任务 done | 询问用户是否运行测试（轻门禁，可默认开） | 测试中 |
| 测试中 | 测试报告 pass | 输出总结，流程结束 | 结束 |
| 测试中 | 测试报告 fail | GATE(缺陷处置)：回架构师修复 / 标记已知问题 | 门禁等待 |

补充规则：

- **失败传播**：并行派发后任一侧失败，同变更另一侧的后续派发动作暂停，走缺陷处置门禁。
- **推进单位**：状态机以单个变更ID 为单位推进；架构师一次产出多个模块变更时，逐变更执行"任务就绪 → 开发 → 测试"循环。
- 串行场景判定依据：看板备注为"前端依赖 `<任务编号-be>` 完成后启动"且前端任务状态为 `blocked`。
- 仅单侧场景判定依据：该变更ID 在看板中仅有一行任务（仅 `-fe` 或仅 `-be`），不存在另一侧任务行，也无 blocked 标记；单侧完成后无交接翻转，直接进入"全部任务 done"检查。

## 看板维护与回读校验

- 项目经理仅翻转**串行交接**状态：be 任务完成并回读确认后，将同变更 fe 任务 `blocked` → `todo`；行定位以 任务编号 + 关联的变更 + 所属模块 组合键，翻转后回读校验。
- `todo → in-progress → done` 由开发者子代理按 task-driven-dev 流程自行维护；项目经理收到完成摘要后**回读校验** done 已落入，不轻信摘要。
- 断点标记（如"等待编码清单确认"、"等待契约违反处理"）由开发者子代理按 task-driven-dev 流程维护：输出 GATE 前写入对应任务行备注，批复后（续接或重派兜底）从断点继续时清除；项目经理只读该标记，用于门禁挂起识别与续跑检测，不代写。

## 续跑入口

启动时执行：

1. `Read /dev-tasks/frontend.md` 与 `/dev-tasks/backend.md`，查找 `in-progress` 任务或备注中的门禁挂起标记。
2. 有 → 按编排状态机对应状态续跑：门禁挂起的任务通过重派子代理重建 GATE（子代理重入检查发现断点未解除会重新输出 GATE），交由用户重新批复。
3. 无 → 按用户输入正常进入新流程。

## 摘要与进度记录

- 要求子代理完成摘要遵循结构：完成了什么 / 修改了哪些文件 / 门禁或结论 / 建议下一步；超长时要求精简，过程细节以文件为准。
- 每阶段结束向用户输出进度摘要；"阶段 → 派发次数 → 结果"可追加记录到 `/dev-tasks/pipeline-log.md`（旁路文件，不影响看板格式，用于会话中断后恢复上下文；GATE 门禁记录亦落于此——挂起时写原文、批复后补记，供中断后人工查阅与重派兜底时取用）。

## 自检清单

- [ ] 每次派发提示自包含：任务说明、任务三元组（开发阶段）、必读清单、GATE 指令齐全；门禁批复后优先续接，重派兜底时附 GATE 原文与批复记录
- [ ] 所有 GATE 均呈现用户批复，未代替用户决策（测试范围默认预批复已注明可否决）
- [ ] 挂起的 GATE 已在呈现前原文落盘 pipeline-log，批复后已补记
- [ ] 并行/串行判定与看板备注一致；串行翻转前后均回读校验
- [ ] 任一侧失败后未继续派发同变更另一侧
- [ ] 看板写入仅限串行翻转的状态列（blocked→todo）；断点标记等备注内容由开发者子代理维护，未代写；此外仅写 pipeline-log
- [ ] 完成摘要中的关键结论已回读文件核实
