##  核心原则
- **契约先行**：任何涉及模块间交互的需求，必须先定义或修改 API 契约。
- **模块划分**：按业务边界和功能独立性进行模块拆分，明确各模块的职责边界，避免跨层耦合。
- **影响优先**：改动前必须评估对数据库、接口、缓存、第三方服务及前端的影响范围。
- **可执行性**：分配给各模块的任务必须具体、可验证，包含明确的输入输出和验收标准。
- **安全与性能**：在设计阶段就考虑鉴权、限流、数据校验、索引优化等非功能需求。
- **数据独立性原则**：数据库设计独立于前端展示需求，基于业务实体关系建模。前端需要的数据格式通过接口层转换，不直接暴露原始表结构。
- **可演进性原则**：接口需有版本化策略（路径版本/头版本/媒体类型版本，由架构师按项目所选协议风格选定），允许增量变更；数据库设计预留扩展字段（如关系型的 `extra` JSON 列、文档型的动态字段），避免频繁改表/改集合结构。
- **反模式警告**：避免各模块共享同一个实体类/数据结构；避免在数据库里存储JSON格式的业务核心字段；避免接口返回数据库全部字段
## 注意

- 按下面的执行步骤进行需求分析，不擅自更改目录结构或流程。
- 设计顺序遵循"数据独立性原则"：先基于业务实体设计数据库，再设计 API 契约，最后设计各模块程序功能。不得因 API 需求反向驱动数据库设计。

## 执行步骤

- 读取需求并在`/requirements/module/`下找到对应的需求模块，理解功能细节、页面设计、验收标准、其他（安全性、质量要求等）。

- 若 `/architecture/README.md` 不存在或内容为空，初始化架构设计说明（包含架构设计思维、各模块技术选型、目录结构约定）；若已存在，仅在技术选型或目录结构发生重大变更时更新。

- **确定需求变更与架构模块的映射**：需求模块与架构模块**不要求同名、不要求一一对应**，按技术边界自由划分程序模块。确定本次需求变更涉及的架构模块（1 到 N 个）：
  - 涉及的每个架构模块，若是新模块，创建`/architecture/module/<模块名称>/`文件夹，并在`/architecture/module/catalog.md`中追加一行（模块名称、简介、备注、状态）。新模块状态填 `active`。若是修改已有模块，按需更新 catalog 中对应行的简介；若本次涉及废弃见后续"废弃流程"步骤。
  - **DB 与 API 契约按整次需求统一设计**（写入全局契约目录，不按模块重复）；但变更ID、模块 change-log、各模块设计文档（`<moduleId>.md`）/ test.md、任务分配均**按架构模块各自独立产出**。
  - **一次架构模块变更只关联一条需求变更**：若发现多个需求变更总是落到同一批架构模块，应提示用户回到需求分析侧合并模块，不在架构侧把多条需求变更聚合进一次架构变更。
  - 记录触发本次设计的需求变更：`/requirements/module/<需求模块>/change-log/<YYYYMMDD>-<序号>.md`（通常为该需求模块 change-log 目录下最新一条；无法确定时与用户确认——派遣模式下并入 GATE(设计确认) 一并上报），后续写入模块 change-log 的"关联需求变更"小节。

- **变更分档（轻量 / 标准）**：完成上述映射后、进入契约设计前，为本次变更定档：
  - **轻量档**（须全部满足）：无数据库 schema 变更、无 API 契约新增或修改、无废弃、仅单个架构模块的内部调整。
  - **标准档**：不满足轻量档任一条件者；首次架构设计必为标准档。
  - 轻量档跳过下述标注"（轻量档跳过）"的步骤；变更ID、模块设计文档、test.md、模块 change-log、任务分配照常执行，其中模块设计文档与 test.md 仅增量更新受影响功能点。档位写入设计概要。

- 读取`/architecture/contracts/database/catalog.md`索引了解现有表/集合清单，仅对本设计相关的表读取其 `.json` 定义文件，理解当前业务实体模型，作为数据库表设计的参考。（轻量档跳过）

- 识别业务实体，设计数据库表结构（基于业务实体关系建模，不预先考虑 API 需要返回什么字段）。（轻量档跳过）

- 读取`/architecture/contracts/apis/catalog.md`索引了解现有接口与数据模型清单，仅对本设计相关的接口读取其接口定义与出入参定义文件，分析是否需要新增/修改 API。（轻量档跳过）

- 读取 `<devManagerPath>/modules.json`，识别本次变更涉及的各代码模块及其类型（`frontend`/`backend`），并列出各模块的功能清单（前端类模块：页面/组件/状态管理/API 调用；后端类模块：控制器/服务/数据访问），作为后续各模块设计文档 `<moduleId>.md` 的输入。

- 基于 DB 设计和功能清单，设计 API 契约（请求/响应格式、错误码、鉴权方式）。响应字段按前端需要裁剪，不直接暴露 DB 全部字段。（轻量档跳过）

- 输出设计概要（包含变更档位、模块归属、DB 设计、API 设计、程序逻辑、变更等信息），按双模式完成人工确认（GATE 类型：设计确认）：手动模式向用户呈现概要并交互确认；派遣模式（由项目经理派发）将概要与待确认问题整理为 GATE(设计确认) 段落（格式见 architect-thinking 技能的"询问方式（双模式）"）输出后立即结束。若通过，继续后续流程，未通过则根据反馈从对应步骤重新分析。

- **确定本次变更的变更ID**：`<任务简介>-<YYYYMMDD>-<序号>`。
  - **任务简介**：5-15 字，**不得含连字符 `-`**（变更ID `<任务简介>-<YYYYMMDD>-<序号>` 靠 `-` 分段解析，含 `-` 会让日期段无法定位）。
  - **`<YYYYMMDD>-<序号>`**：作为本次模块 change-log 文件名。日期为今天，序号为当天该模块 change-log 目录下**已有文件的最大序号 +1**（当天首个变更序号为 0）；用 `Glob /architecture/module/<模块名称>/change-log/<YYYYMMDD>-*.md` 确认序号，无匹配文件则序号为 0。
  - **按模块独立确定**：本次需求变更涉及多个架构模块时，每个模块各自确定一个变更ID（序号按各自模块的 change-log 目录计）。变更ID 仅在模块内保证唯一，跨模块可能重名。
  - 变更ID 一经确定，后续 DB change-log、废弃横幅、模块 change-log、任务看板均引用此变更ID，**不得更改**。

- 将变更后的数据库表/集合写入到`/architecture/contracts/database/`下，统一使用 `.json` 中立描述（字段、类型、约束、索引的元数据，由开发者按目标数据库类型映射为具体 DDL 或 schema 验证），并更新目录`/architecture/contracts/database/catalog.md`。每张表须在 JSON 中写明 `owner`（归属模块 ID，取拥有该表的后端模块，见 `modules.json` 的 `owner` 字段），并在 catalog 的"归属模块"列同步登记。示例请参照`/templates/database-contract-template/users.json`，注意，按示例文件的格式进行编写，不得额外添加内容。（轻量档跳过）

- 若本次设计涉及数据库 schema 变更（新增表/改字段/删字段/改索引/改约束/废弃表），为**每张受影响的表**在`/architecture/contracts/database/change-log/<表名>.md`下追加一条变更记录。文件不存在则按`/templates/database-contract-template/change-log-template.md`的格式新建；已存在则在文件顶部（倒序）追加新条目。每条记录须包含：**变更类型**、**破坏性变更**（是/否及说明）、**变更详情**（字段/索引级逐条列出）、**迁移说明**（无则填"无"）、**关联模块变更日志**（指向本次将生成的模块 change-log 路径，并注明本次变更的**变更ID**，格式为`<任务简介>-<YYYYMMDD>-<序号>`）。本次未涉及 schema 变更的模块跳过此步。变更ID 用于变更级交叉引用，不带模块后缀；任务看板通过独立的"关联的变更"列记录变更ID，任务编号（`<任务简介>-<moduleId>`）与变更ID 解耦。（轻量档跳过）

- 将新api接口更新到`/architecture/contracts/apis/interfaces/`，每个接口对应一个文件，将接口出入参定义更新到`/architecture/contracts/apis/params/`下，每个数据模型对应一个文件。每个接口文件须在"接口信息"块写明**提供方**（实现该接口的后端模块 ID）与**消费方**（调用该接口的模块 ID 列表，由 `modules.json` 的 `dependsOn` 推导）。最后更新`/architecture/contracts/apis/catalog.md`目录，接口与数据模型表格的"状态"列对新接口填 `active`。示例请参照`/templates/api-contract-template/`文件夹下对应文件，注意：按示例文件的格式进行编写，不得额外添加内容。（轻量档跳过）

- 对本次变更涉及的每个代码模块，生成该模块的程序功能，细化到该模块类型对应的粒度（前端类模块：页面/组件/样式/状态管理/API 调用；后端类模块：控制器/服务/数据访问/单元测试），注意：不要写具体的实现代码。

- 将每个涉及模块的程序功能写入到`/architecture/module/<模块名称>/<moduleId>.md`（文件名取模块 ID；仅涉及模块出文件，未涉及模块不出）。

- 生成功能测试用例，覆盖正常路径、边界场景和异常场景，明确输入数据与预期结果，注意：不要写具体的实现代码。

- 将功能测试用例写入到`/architecture/module/<模块名称>/test.md`，结构参照`/templates/test-template.md`（按功能点分节、用例强制稳定编号、每条用例四要素：描述/输入数据/预期结果/类型）。

- 若 `/tester/config.md` 不存在或为空，初始化测试配置骨架（参照 `/templates/tester-config-template.md`：测试账号（全局）+ 测试工具（按模块）+ 测试环境（按模块）），按 `modules.json` 的模块清单为每个模块填写单元测试命令与服务地址占位，工具选型参照 `/architecture/README.md` 记录的各模块技术栈；账号细节由用户后续填充，架构师只产出骨架。已存在则仅在工具/环境发生重大变更时更新，否则不动。（轻量档跳过）

- 若本次设计涉及**废弃**（接口废弃 / 模块设计文档部分功能废弃 / 模块整体废弃），按以下流程处理；本次未涉及废弃则跳过本步：
  - **接口废弃**（原地标注，不移动文件）：
    - 在 `/architecture/contracts/apis/catalog.md` 中将对应接口行的"状态"列改为 `deprecated`（永久下线改为 `archived`）；若该接口独有的数据模型不再被任何活跃接口引用，数据模型表对应行同样改状态。
    - 在对应 `interfaces/<接口名称>.md`（及 `params/<数据模型名>.md`）文件**顶部**追加废弃横幅，格式严格如下（占位项按实际填写，`<变更ID>` 为 `<任务简介>-<YYYYMMDD>-<序号>`，不带模块后缀）：
      ```
      > **已废弃**（<变更ID>，废弃日期 <YYYY-MM-DD>）：<废弃原因>。详见 [模块变更日志](../../../module/<模块名称>/change-log/<YYYYMMDD>-<序号>.md)。
      ```
    - 不得删除接口/数据模型文件本身，也不得移动到其他目录——历史 change-log 与 catalog 的相对链接必须保持有效。
  - **模块设计文档（`<moduleId>.md`）部分功能废弃**：
    - 在对应文件末尾追加或更新 `## 已废弃` 小节，条目格式：`- <功能名称>（<变更ID>，<YYYY-MM-DD>）：<废弃原因>。详见 [模块变更日志](./change-log/<YYYYMMDD>-<序号>.md)。`（`<变更ID>` 为 `<任务简介>-<YYYYMMDD>-<序号>`，不带模块后缀）
    - 不删除原功能描述正文，保留可追溯；对应模块 catalog 行状态改为 `deprecated`。
  - **模块整体废弃**（归档移动）：
    - 将 `/architecture/module/<模块名称>/` 整体移动到 `/architecture/module/_archived/<模块名称>/`，模块下的 `<moduleId>.md`/test.md/change-log/ 原样保留作为历史档案。
    - 在 `/architecture/module/catalog.md` 中将对应行的"状态"列改为 `archived`，保留行不删除。
    - 模块涉及的接口按"接口废弃"流程在原位标注；涉及的表按 DB change-log "废弃表"变更类型记录（已在数据库变更日志步骤覆盖）。
  - **模块 change-log 记录**：本次模块 change-log（模块整体废弃时为归档前最后一条）须包含一个**废弃内容**小节，列出废弃的接口、表、功能点及变更ID，与各废弃文件顶部的横幅构成双向引用。

- 变更内容写入到`/architecture/module/<模块名称>/change-log/<YYYYMMDD>-<序号>.md`（文件名即确定变更ID 时定的编号）。文件**首行**显式记录变更ID，格式：`# 变更ID: <变更ID>`。变更内容须包含一个**关联需求变更**小节：指向触发本次设计的需求变更日志`/requirements/module/<需求模块>/change-log/<YYYYMMDD>-<序号>.md`（需求模块与架构模块不要求同名，凭此小节回溯需求来源）。本次需求变更涉及多个架构模块时，还须包含一个**关联变更**小节，列出同次需求变更在其他架构模块产生的变更ID 及其 change-log 路径，各模块 change-log 之间据此互相引用。变更内容须包含一个**数据库变更**小节：若本次涉及 schema 变更，列出每张受影响表名、变更类型、是否破坏性，并给出指向`/architecture/contracts/database/change-log/<表名>.md`的链接；若未涉及 schema 变更，注明"无"。该小节与数据库 change-log 构成双向引用，变更ID 保持一致。若本次涉及废弃，还须包含上一步所述的**废弃内容**小节。变更内容还须包含一个**受影响功能点**小节，列出本次变更涉及的 test.md 功能点名称（与`/templates/test-template.md`中的`## 功能点：<名称>`一致）；若本次未涉及功能点变更（如纯 DB schema 变更无功能影响），注明"无"。测试者据此圈定增量测试范围。

- 对照核心原则进行自检，发现问题需回到对应步骤修正：
  - **档位一致**：设计概要已写明变更档位？轻量档判定成立（无 schema 变更、无契约增改、无废弃、单模块内部调整）且已跳过标注"（轻量档跳过）"的步骤、未产出多余的契约变更？
  - **契约先行**：所有模块间交互是否都有对应的 API 契约定义？
  - **数据独立性**：DB 表是否基于业务实体建模，而非按 API 响应字段反推？
  - **可演进性**：API 是否定义了版本化策略（路径/头/媒体类型之一）？DB 是否预留扩展字段？
  - **反模式**：是否避免了各模块共享实体类？API 响应是否裁剪而非返回 DB 全字段？是否避免了 DB 存储 JSON 业务核心字段？
  - **变更可追溯**：涉及 schema 变更的每张表是否都已在 `/architecture/contracts/database/change-log/<表名>.md` 追加条目，且与模块 change-log 双向引用、变更ID 一致？
  - **变更ID 一致**：DB change-log、废弃横幅、模块 change-log 首行、（若已分配任务）任务看板"关联的变更"列中的变更ID 是否全部逐字一致，与"确定变更ID"步骤定下的值相同？模块 change-log 首行是否已按 `# 变更ID: <变更ID>` 格式记录？
  - **需求追溯**：模块 change-log 是否包含"关联需求变更"小节并指向对应的需求变更日志？本次涉及多个架构模块时，各模块 change-log 是否都包含"关联变更"小节且互相引用？
  - **废弃可追溯**：废弃的接口/数据模型是否在 `apis/catalog.md` 标注状态、文件顶部追加废弃横幅并指向模块 change-log？模块设计文档部分废弃是否归入 `## 已废弃` 小节？模块整体废弃是否已移至 `module/_archived/<模块名称>/` 且 catalog 状态改为 `archived`？模块 change-log 是否包含"废弃内容"小节？
  - **受影响功能点**：模块 change-log 是否包含"受影响功能点"小节（无功能影响时注明"无"），与 test.md 功能点分节名称一致，供测试者增量测试圈定范围？
  - **测试配置**：`/tester/config.md` 是否存在（首次架构设计时应初始化骨架，参照 `/templates/tester-config-template.md`，工具选型参照 `architecture/README.md`）？

- 总结出变更概览。
